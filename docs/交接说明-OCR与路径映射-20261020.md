## 一、这一轮到底做了什么（按时间顺序）

### 1. PDF 提取换引擎（根因修复）

**问题**：花生壳盒子手册"扫描版"只提取出 129 字。
**真因**：`pypdf` 遵守 PDF 的「页面提取：不允许」权限位 → 直接不给。
**改法**：`app/extract.py::_pdf_text()` 改成**先 PyMuPDF(fitz)、失败再 pypdf**。
**效果**：129 字 → **12488 字**。

### 2. 扫描版 PDF 自动 OCR（全链路）

| 文件 | 作用 |
|---|---|
| `app/ocr.py` | 四引擎统一入口：`mineru`（结构化 Markdown+提图）、`ppocr`（PP-OCRv6 GPU，0.4~2.4 秒/页）、`ppocr_cpu`、`rapid`（纯 CPU 兜底）。全走**子进程桥接**，不污染本项目环境 |
| `app/indexer.py::_ocr_pdf_text()` | PDF 提不出正文时调 OCR，文字切块入库，**超限提示写进 files.note** |
| `app/ocr.py::pdf_text_density()` | ★**判据**：每页字数 < 50 才算扫描版 |

> ⚠ **踩过的坑（重要）**：最初判据是"提取出的文字为空"。实测地藏经 160 页**有 494 字**（扫描页上零星的页码/拼音），
> 于是被判成"文字版"→ 跳过 OCR → **正文一个字都进不了库**。
> 必须看**密度**，不能看"空不空"。

### 3. PDF 插图打标（三档 + 模型可选 + 队列）

| 文件/表 | 作用 |
|---|---|
| `app/pdfimages.py` | 筛真插图：尺寸≥120px、占页≥2%、按 sha1 去重、每份最多 N 张。实测花生壳手册 **440 个图对象 → 71 张真插图** |
| `caption_queue` 表 | 登记/去重/状态（pending/done/failed/skip）/统计 |
| `app/caption_run.py` | 执行器：取队列 → 抠图(fitz) → 打标(本地/外部) → 编码(该文件夹维度) → 存 `kind='caption'` 片段，文案带 **「[第 N 页 插图]」** |
| `folderconf.KEYS` | 新增两个**每文件夹**字段：`caption_mode`（off/queue/auto）、`caption_model`（local/remote）|

**实测质量**（第 6 页）：
> `[第 6 页 插图] 设备接口示意图。黑色方形设备，顶部有标志，侧面可见网线接口和电源接口，虚线连接说明。标注："网线接口""电源接口""连接路由器/交换机""连接电源"。`

> ⚠ **踩过的坑**：写得太像"任务说明"时，模型会把**要求本身**也复述出来 ✗
> （入库成了「我们需要回答用户。用户要求：这是一份 PDF 文档里的插图…」）
> 两处修：① 提示词明确禁止复述；② `_caption_text()` 按句丢掉开头的过程语言。

### 4. 显存互斥（项目主的核心担心）

**原话**：「OCR 与打标同时进行，本地方案不是要撞显存？这个需要给个顺序进行才行」

| `app/ocr.py::gpu_slot` | 用显存的活**串行**；调外部 API 的**不进锁**（天然并行）|
| `gpu_status()` | 返回 `{holder, waiting, locked}` → 界面显示「🎮 显卡占用：OCR(ppocr)（排队 2）」|

**实测**：两个本地活 2.40 秒（串行）vs 本地+API 1.20 秒（并行）。

### 5. 页数限制（三轮迭代到最终形态）

| 项目主原话 | 最终做法 |
|---|---|
| 「页面限制太死板，默认 100 以内，要给提示和调节」| `ocr_max_pages`，超限提示写进 files.note |
| 「干脆做成默认自动，按实际页码全部 OCR，根据 8G 显卡限制进程数」| `ocr_max_pages=0` = **全部做**；`auto_batch()` 按可用显存算批量（实测 7140MB → 8 页/批）|
| 「调高页码数后，原已 OCR 的页面不会重新 OCR 吧」| `files.ocr_pages` / `ocr_limit` 记进度；`ocr_pdf(start_page=)` **从断点续**；`_ocr_wants_resume()` 让"上限调大"的文件不再被跳过 |
| 「给个 pdf 文件选择页码范围，不要只能从第一页算」| `ocr_page_from`/`ocr_page_to`（全局）|
| 「应该是要某个特定 PDF 单独设，以个别设置为准」| `files.ocr_from`/`ocr_to`，**优先级最高**；搜索结果的 PDF 行有「📄 页码」按钮 |

**最终优先级**：单份 PDF 设置 > 全局页码范围 > 断点续做起点。

### 6. 计划 / 全力执行

| 端点 | 作用 |
|---|---|
| `POST /api/index/plan` | 📋 只算不做，**0.19 秒**秒回（不扫目录、不调模型）|
| `POST /api/index/run-plan` | 🚀 编排：① 腾显存(嵌入模型挪 CPU) ② 索引 ③ 插图打标 ④ 收尾(停 MinerU + 挪回)|
| `GET /api/gpu/status` | 显卡占用 + 引擎清单 + 夜间任务状态 |
| `_deadline_from()` | `max_hours` / `until`（`until` 已过会顺延到明天）|

> ⚠ **踩过的坑**：`filesearch.py` 是 `create_router()` 工厂，**里面没有 `app`** ✗
> 用了 `app.state` → `NameError` → 接口 500。改成模块级 `_LAST_PLAN` / `_NIGHT`。

### 7. 本机 ↔ 服务器 路径映射（最后一块）

**项目主原话**：「服务器上没挂载电脑上正在使用的 NAS 盘符，导致服务器不能定位文件……
我桌面版用了 `\\NAS\photo\家庭相册`，它旁边应该有个服务器对应的路径可以自定义，
现在对应 `/mnt/nas_photo/家庭相册`……这样本机与服务器的相对转换数据库才能共享」
+ 「**本机的文件夹也需可以自定义设置同步目录**」
+ 「这个功能**只需添加到本机版**即可，服务器版上不用」

| 改动 | 说明 |
|---|---|
| `folders.server_path` | 服务器视角路径（空 = 自动建议）|
| `folders.local_alias` | 本机实际目录（空 = 用 path）|
| `app/serverpath.py` | `split_unc()` / `candidates()` / `suggest_server_path()` / `pick_root()` / `to_server_path()` / `is_server()` |
| `GET/PUT /api/folders/{id}/paths` | 界面读写这两个路径 |
| `_folder_root()` / `_to_this_host()`（filesearch）| 索引根、授权根、预览、打开文件全都按"这台机器视角"解析 |
| `_can_index_here()` → 前端 `is_builder` | 「🔗 路径」按钮**只在本机版显示** |

> ⚠ **为什么加两列而不改 `path`**：`folders.path` 是 `files.path` 的前缀（权威键）。
> 直接改会**牵连整个索引**。用 `local_alias` / `server_path` 只是换"去哪儿找"，索引关联永不断。

**服务器 fstab 新增**（原来没挂）：

> ⚠ **踩过的坑**：`Shared` 里的连字符没去掉 → 猜成 `/mnt/mnt_yq-sync` ✗

## 六、这一轮踩过的坑（省得再踩）

| 现象 | 真因 | 修法 |

### 2.5 界面：PDF 插图打标（队列）—— 2026-10-20 下午补的

项目主原话：
> 「现在只有针对文件夹打标按钮，那就在旁边增加一个 PDF 插图的打标按钮吧，我手动也方便，
>   也要可以随时暂停开始功能及并到计划中，让晚上全力执行功能」
> 「现在项目在图片打标，我在项目界面也看不到进程啊，这个我怎么监控？后台在干嘛也不知道」

以前 caption_queue（PDF 里的插图）**只有后台线程在跑，界面上只有一个待标数字** ✗
现在 ⚙ 设置 →「图片打标」卡下面多了「**PDF 插图打标（队列）**」：

| 元素 | 作用 |
|---|---|
| ▶ 开始打标 | 后台跑，**一路跑到队列空**（跑完自动接下一批）；界面立刻返回，不会把请求挂死 |
| ⏸ 暂停 / ▶ 继续 | 当前这张做完就停住，随时接着跑；不杀线程、不丢进度 |
| ⏹ 停止 | 停住，**剩下的留在队列里**，下次接着跑 |
| 进度条 + 状态 | 每 2 秒刷新：待标/已完成/失败、本批第几条、正在处理哪份文件（第几页）、每张约多少秒、全部跑完约多久、用的是哪个模型、来源（手动 / 🚀 全力执行） |

配套代码：

| 文件/位置 | 作用 |
|---|---|
| caption_run._RUN + 
un_state() | 进程内运行状态（界面读它画进度） |
| caption_run.pause()/resume()/stop()/_gate() | 暂停用标志位，循环里自己等；不杀线程 ✓ |
| caption_run.start_async() | 后台线程跑，内部**分批循环到队列空** |
| 
un_queue(source=, claim=) | source 只用于界面显示来源；claim=False 表示状态由 start_async 管 |
| GET /api/caption/queue/status<br>POST /api/caption/queue/start/pause/resume/stop | 五个端点（管理员） |

> ⚠ 和「图片打标」那张卡的区别：那张卡给**图片文件**打描述（pp/caption.py，会挪嵌入模型腾显存）；
> 这张卡给 **PDF 里抠出来的插图**打描述（caption_queue，走外部 API 时可并行）。
> 两者进度互不相干，都显示在各自卡片里。

> ⚠ 夜间「🚀 全力执行」也走同一个状态 → 那张卡会显示「来源：🚀 全力执行」，进度照样实时 ✓
