### ⑤ 知识库检索加强 —— 第一步（FTS5 + RRF）✅ 本轮完成
新模块 `app/ftsindex.py` + `store.py` / `searcher.py` / `filesearch.py` / `caption.py` 的接入。

**为什么不是"直接给 text 建 FTS5"**（实测数据，都在 7.6M 字 / 4.9 万片段上跑过）：

| 方案 | 建索引 | 库增量 | 「家谱」「报销」这类**两字**中文 |
|---|---|---|---|
| trigram（原样文本） | 4.2s | +171MB | **0 条** ✗（trigram 至少要 3 个字）|
| bigram + detail=none | 4.0s | +139MB | 短语查询不支持 ✗ |
| bigram + detail=full | 4.6s | +92MB | 0 条 ✗（切法不对，见下）|
| **逐字 + 短语 + detail=full** | **1.8s** | **+33MB** | **4 条 ✓ 与 LIKE 真值一致** |

做法：入库时把正文切成"单字之间夹空格"存进 `chunks.uni`，查询词也切成单字做成
**短语**（`"家 谱"`）⇒ 语义上就是**子串匹配** ✓，中英文一样（`"2 0 2 4"` 能命中 "2024年"）。
索引不用手工维护：`content='chunks'` + 三个触发器（insert/delete/update）✓
（实测：增/改/删 chunks，FTS 立刻跟着变 ✓）。

**带来的变化**：
- `/api/search`：向量 + 文件名 + **FTS** 三路 **RRF 融合**（权重 1.0 / 0.8 / 1.1，
  K=60，与 `store.hybrid_search` 同口径）→ 响应里多了 `fts` 计数，每个结果带
  `channels`（哪几路命中）✓；没有关键词命中时**完全走老逻辑**（老行为不变 ✓）
- `/api/kb/retrieve`：命中片段直接进上下文，标 `channel=fts` ✓
- `/api/chat`：原来的 `chunks.text LIKE '%kw%'` 全表扫（**每个词 50~400ms** ✗）
  换成 FTS5（**1~40ms** ✓），LIKE 只作为"索引没建起来"时的兜底 ✓
- 效果对照（`run\bench_retrieval.py`）：10 个真实查询里，FTS **提供了 49 个
  「文件名/路径之外」的文件级命中** —— 这些以前只能靠慢速 LIKE 才拿得到 ✓
- 真实请求实测：`/api/search?q=报销` → 前 3 条全部 `channels=['fts']` ✓；
  `/api/kb/retrieve` 的「报销」5 条片段全部来自 fts ✓；
  日志出现 `知识库关键词兜底（FTS5）…补 2 个文件` ✓

**踩到的坑（关键）**：对 `content=` 外部内容表，`SELECT COUNT(*) FROM fts` 会被
SQLite 直接从内容表回答 —— 刚建完、索引还是空的时候也返回 5 万 ✗，
`SELECT COUNT(*) FROM (SELECT rowid FROM fts)` 同样不可靠 ✗。结果第一版 `ensure()`
"对账没差异 → 不 rebuild"，索引一直是空的、**所有查询 0 条** ✗。
现在改成**真 MATCH 一次**判断索引死活（`_index_alive()`）✓。

**代价**：库 +33MB（285.6 → 318.8MB，推库时间 +约 12%）、启动时一次性回填 5~7s
（之后每次启动 0.86s ✓）。**未做**（按用户定的优先级排后面）：HyDE、分块/文件名加权、rerank。

**剩下的三步（按性价比顺序）**：② HyDE（复用服务器上已有 llama-server）、
③ 分块/文件名加权、④ rerank。

### ⑥ 索引加速（NAS 那 6 分钟）—— ✅ 本轮完成

## 5. 铁律与踩坑（**最容易重犯的**）

### 改代码的规矩
1. **改端点前先 `read` 完整签名** —— 今天两次 500 都是忘了加 `request: Request` ✗。
2. **验证写接口不要发"部分 config"** ✗（2026-10-17 真事故）：
   `PUT /api/folders/{id}/config` 是**整体替换** —— 我为了试一个键，
   发 `{"config": {"fast_scan": false}}`，把项目主设的 `use_kb` 抹掉了 ✗。
   现在响应里有 **`dropped_keys`** ✓：发完**必须看一眼**；
   只想改一个键就带 `merge: true` ✓，或者先 GET 拿全量再改 ✓。
3. **改完必须真发一次请求**（不是只看"编译通过、已重启"）—— 这一步救过两次场 ✓。
4. **每完成一小步就拍快照**（本机 `run/snapshot.py "说明"`、服务器 `snapshot_server.sh`）。
5. 动数据库结构/同步链路**之前**额外拍一次服务器快照。
6. 合并一律**并集语义**：不删账号、不删文件夹、不改 path。
7. **改 `.bat`（GBK 文件）只能用字节级替换** ✓：`✓`/`→` 这类符号**不在 GBK 里**，
   直接写会 `UnicodeEncodeError` ✗ —— 而 `write_text()` 是"先截断再编码"，
   一失败文件就变 0 字节 ✗（本项目真清空过 run_server.bat）。
   正确姿势：读 bytes → 替换 → 写 `.tmp` → 校验 → `os.replace()` ✓
   （`start.bat` 这次第一次替换就因 `✓` 编码失败，靠校验保住了原文件 ✓）。
8. **对「用户给的路径 / 网络盘」不要直接 `resolve()`** ✗：
   `Path.resolve()` 会 realpath —— 碰到**凭据失效的映射盘**会抛
   `OSError WinError 1326` ✗，一个坏盘就能把整个接口打成 500 ✗
   （⑪ 就是这么炸的）。用 `app\pathutil.py` 的 `safe_resolve` ✓
   和 `norm_key` ✓（后者纯字符串、不碰磁盘）。
9. **服务退出时别去动用户看得见的东西** ✗（⑱ 的教训）：
   "服务退出时关界面窗口"看起来很贴心，但我**重启服务**也走退出流程 →
   把项目主正开着的界面关了 ✗（他为此投诉两次）。
   加任何"退出时做某事"之前，先问：**如果是我自己重启，会发生什么？**
10. **重启用 `run\restart_server.py`** ✓，不要手拼命令行：
   手拼会起无标题野黑框、旧服务窗口残留、还可能让旧进程占着端口却"看着像重启成功" ✗。

### 平台/工具坑（都已踩过）
| 坑 | 现象 | 对策 |
|---|---|---|
| PowerShell 吃掉内层双引号 | 命令语法错 / `ssh` 报 unexpected token | 命令里**别用双引号**；复杂命令写成**脚本文件 scp 过去**，或 base64 包裹 |
| `.bat` 是 GBK | read/edit 工具报 "invalid UTF-8" | 用 `-Encoding ansi` 读写；或改用 Python 脚本代替 |
| **`Path.write_text()` 改 .bat** | 它**先 truncate 再编码**：一旦编码失败，文件直接变成 0 字节 ✗（本轮真把 `app/run_server.bat` 清空过，靠 snapshot 里的副本恢复 ✓）| 改这类文件：**纯字节级替换** + 先写 `.tmp`、校验长度/内容、再 `os.replace()` 原子替换 ✓；动手前先 `len(raw) > N` 兜底 ✓ |
| **FTS5 外部内容表 `COUNT(*)`** | 对 `content='chunks'` 的 FTS 表，`SELECT COUNT(*) FROM fts` 会被 SQLite **直接从内容表回答**（索引空着也返回 5 万 ✗），`COUNT(*) FROM (SELECT rowid FROM fts)` 同样不可靠 ✗ → "对账没差异就不 rebuild"，索引一直空、查询全 0 条 ✗ | 判断索引死活只能**真 MATCH 一次**（拿内容表里第一个 token 查一下，0 条就是空 ✓，见 `app/ftsindex.py::_index_alive`）|
| 控制台 GBK | 打印 `✓✗⚠` → `UnicodeEncodeError` | 脚本开头 `sys.stdout.reconfigure(errors="replace")`；或别用这些字符 |
| SQLite 触发器 | 合并写入的 `updated_at` 被刷成"现在" → 永不幂等 ✗ | 写完设置后**补一条只改 `updated_at`** 的 UPDATE ✓ |
| 时间戳精度 | `strftime('%s')` 只到秒 → 同秒各改一次会永久不一致 ✗ | 用 `(julianday('now')-2440587.5)*86400.0`（小数秒）|
| 测试隔离 | 临时配置键名写错 → 测试写进**真实库**污染 ✗ | 传**只带 `db_path` 的最小替身对象**，不碰 Config 内部 |
| 账号身份 | 两边自增 id 会撞车 → `UNIQUE constraint failed` | 账号身份是 **`name`**；文件夹设置身份是 **`id`**（同一份库推过去的）|
| `scp` 参数 | 传 `str` → `'str' object has no attribute 'relative_to'` | `scp()` 要 `Path` |
| 热重载 | 只 rebind 一处 → 别处握着关掉的连接 → 设置页 500 | `app/dbreload.py` 的钩子机制（都已登记）|

## ⑬ 扫描前清洗规则（入库前必过的一道关）

**位置**：`app/extract.py::clean_text()` —— 索引时**自动执行**，不需要任何开关 ✓
**兜底**：`app/extract.py::hard_clean()` —— 正常清洗后仍编不过时，索引器**自动再洗一次** ✓
**独立工具**：`clean_text.py`（同一套规则，可单独拷走给别人用 ✓）

### 洗掉什么（按实测踩坑顺序，每一条都是真事故）

| # | 清掉什么 | 为什么必须清 |
|---|---|---|
| 1 | 控制字符 `\x00-\x08 \x0b\x0c \x0e-\x1f \x7f` | 嵌入模型直接报 `TextEncodeInput must be Union[...]` ✗ |
| 2 | 零宽字符 `U+200B-200F` `U+202A-202E` `U+2060` `U+FEFF` | 同上；而且它们会污染检索（看着一样的词搜不到）|
| 3 | **孤立代理字符** `U+D800-U+DFFF` | ★★ **2026-10-19 挖到的真凶**：PDF 里的 emoji（`🌟` = `\ud83c\udf1f`）被提取工具**拆散**，只剩一半 `\ud83c` → 它不是合法字符 → tokenizer 拒收**整片** ✗（实测：某片 996 字，第 389 个字符就是它）|
| 4 | URL 编码噪声行（`%2F` ≥3 个；或 `&`/`=` ≥3 个且无中文；>40 字）| 微信剪藏的图片链接被当正文切块，检索命中它、模型只能答"资料里没提到" ✗ |
| 5 | 连续空行压成一个、行尾空白 | 片段更干净、省空间 |
| 6 | **（hard_clean 才知道的）** 私有区 `U+E000-F8FF`、非字符 `U+FFF0-FFFF`、**所有非 BMP 字符** | 兜底：还有 tokenizer 挑剔的字符时，全丢掉也要让文本进库 ✓ |

### 处理孤立代理的策略

- **能配对的**（`\ud83c\udf1f`）→ **重组成 `🌟` 保留** ✓
- **配不上的半个** → **删掉** ✓（宁可少一个 emoji，也不能让整片文字进不了库）

### 三层保险（保证"以后不再碰到就报错"）

1. **入库前清洗**（`clean_text`）—— 常规情况在这里就干净了 ✓
2. **逐片重试**（`indexer.flush`）—— 批量里有一片编不过，**不会毁掉整批** ✓
   失败的那片会**单独重试**，并按文件记录明确原因 ✓
3. **强力清洗兜底**（`hard_clean`）—— 逐片仍失败 → 再洗一遍（丢代理/私有区/非 BMP）重试 ✓
   日志会写：`文本片用「强力清洗」后编码成功（N 字 → M 字）`

### 铁律

- **任何新的"提取文本"入口都要过 `clean_text`** ✓（否则脏字符会直接喂给模型）
- **改了清洗规则，必须同步改 `clean_text.py`**（独立工具），两边保持一致 ✓
- ★ **改完代码必须 `run\restart_server.py`** —— `run\deploy\deploy_app.py` **只同步到服务器、不重启本机服务** ✗
  （2026-10-19 踩过：因为没重启，服务跑了 2.5 小时旧代码，一连串"修好了却没生效"都出在这 ✓）

### 再遇到"扫描报错"的排查套路

1. 界面上点那个 **「N 异常」** → 直接看**具体文件名 + 完整路径 + 原因** ✓
2. 若是 `TextEncodeInput must be Union[...]` → **几乎肯定是文本里有脏字符** ✓（不是文件坏了）
3. **二分定位元凶字符**（这个方法实测 10 步内就能找到）：
   ```python
   # 能过 → 往后；不过 → 往前
   lo, hi = 1, len(piece)
   while lo < hi:
       mid = (lo + hi) // 2
       if encode_fails(piece[:mid]): hi = mid
       else: lo = mid + 1
   print(piece[lo-1], hex(ord(piece[lo-1])))   # 就是它
   ```
4. 把该字符（或它的 Unicode 类别）加进 `clean_text` 的清洗表 ✓
5. **`restart_server.py`** → 重扫那个文件夹 → 异常清零 ✓
