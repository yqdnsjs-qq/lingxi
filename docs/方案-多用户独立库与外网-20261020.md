# 建议方案 · 服务器版多人化 + 本机版节点化（2026-10-20）

> ## ⚠ 2026-10-20 晚 · 项目主定调（以此为准，下文"一人一库"的方向作废）
>
> 项目主明确了架构，和最初这版方案有实质差别，**以下面这条为准**：
>
> **服务器 = 共享主库 + 索引共用；隔离的是「归属和可见性」，不是物理分库。**
>
> | 项 | 定调 |
> |---|---|
> | 数据库 | **不分库**。服务器仍是一个主库，大家检索同一份索引 |
> | 隔离 | 靠 `folders.owner_id` + `visibility`（共享/私有）+ `folder_acl`（指定人可读），这套已经有 |
> | 索引 | **共用**。服务器上只有**管理员**能建索引（以建库机为权威），本机各管自己的文件夹 |
> | 打标 | 挂在主库上，**默认只有管理员可用** |
> | 备份 / 快照 | 同上，管理员专属 |
> | 模型 API | 管理员设的 = **所有人的默认**；**用户可自己覆盖**（各自用各自的） |
> | 个人爱好 | 折叠状态、上次标签页、视图模式等，**永远只写自己** |
> | 本机版 | **个人专用**（单人多机），不做多人隔离 |
>
> 一句话：**"数据独立"是指"谁的东西谁能看见、谁能用"，不是"每人一个库文件"。**
> 所以下文第四节的"一人一库"、第五节的阶段 0/2（拆库 + 对象级同步）**都不做**；
> 真正要做的只剩：偏好分层（已完成 ✓）+ 共享/私有语义打磨 + 外网与注册审核。

> 这份是**方案讨论稿**，不是已实现的说明。看的时候重点看第五节「分阶段」和第六节「风险」，
> 第七节是我建议的**第一步**（代价最小、马上能验证方向）。

---

## 一、一句话结论

现在这套是「**一台机器的知识库，备份到另一台**」；
你要的是「**一台服务器 = 多个人的独立知识库 + 共享区**」。

这不是加几个开关能到位的，**根子在数据库和同步方式**：
现在是「一个库 + 整库推送」，要变成「一人一库 + 按文件夹同步」。
所以建议**分四步走**，先把地基（一人一库）换掉，再谈共享、外网、注册。

---

## 二、现状（三条硬约束，正是要改的地方）

| 位置 | 现在是什么 | 为什么挡住你的目标 |
|---|---|---|
| `app/config.py` 的 `db_path` | 写死 `data/index/index.db` **单库** | 一个进程只认一个库，做不到"每人数据独立" |
| `meta` 表 | 只有 `(key, value)` 两列，**没有 user_id** | 界面偏好（含**你的模型 API 密钥**）是**全局一份**，多人用会互相覆盖 ✗ |
| `run/deploy/sync_db.py` | **整库推送 / 整库拉回** | 多人各自的本机库一推，就把别人的库整个盖掉 ✗ |

另外两个已经**做对**、可以直接沿用的：

- `folders.visibility`（shared/private）+ `folder_acl`（指定谁可读）—— **共享/私有的语义已经有了**
- `users` / `sessions` / `auth.py`（含登录限流）+ `multiuser.py`（可读/可写范围）—— 账号体系是现成的

## 三、把你要的拆成 6 条可执行需求

1. **一人一库**：每个用户的文档、片段、向量、人脸、队列，全在自己的库里
2. **共享 / 私有**：自己定的东西，可以只给自己，也可以分享给指定人（或全站）
3. **本机 → 服务器的对象级同步**：只推"我自己的文件夹"，不再整库覆盖
4. **网页端能看到"我的库" + "别人共享给我的库"**，检索时两边一起查
5. **模型 API 各用各的**；服务器上那台机器的本地模型**共用**（排队用）
6. **外网可访问 + 注册开关 + 管理员审核**

> 你说的"能在网页端使用各自本机服务"——我按**数据服务**理解（网页端能用到"我自己本机同步上去的知识库"）。
> 如果你指的是"网页端要调用我本机的显卡替我干活"，那是**节点模式**，成本要高一个量级，
> 见第八节的说明，**建议先不做**。

## 四、推荐架构

### 4.1 数据怎么放

```
服务器 /home/lingxi/data/
  shared/index.db          ← 公共库（管理员维护，全站可搜）
  users/
    1/index.db             ← 用户 1 的私有库
    1/prefs.json           ← 用户 1 的偏好（模型地址/模型名/密钥，加密存）
    2/index.db
    2/prefs.json
```

- **每库仍是原来那套 schema**（folders/files/chunks/caption_queue…）→ 代码改动面小 ✓
- 备份直接按库文件做（`dbbackup.py` 已经能按文件做页级增量，**天然支持多个库** ✓）
- 某个用户的库坏了，**只坏他一个**；删号 = 删目录，干净利落 ✓

### 4.2 检索怎么查（关键设计）

一次查询要跨三类来源，**不能用一条 SQL**，用"联邦检索"：

```
① 我的库（全量）
② 别人共享给我的库（按 share 表：folder_id → 允许谁读）
③ 公共库
→ 各自查、各自打分 → 合并排序 → 来源上标注「来自 张三 的共享库」
```

- 每库有自己的 FTS 索引和向量索引，并发查（3~5 个库的延迟基本可忽略）
- 排序用现有的 `searcher` 分数口径，保持结果可比

### 4.3 共享怎么表达

在现有 `folders.visibility` + `folder_acl` 之上加一层：

```sql
-- 共享发布表（谁把哪个文件夹共享出去了）
CREATE TABLE shares(
  id INTEGER PRIMARY KEY,
  owner_id INTEGER NOT NULL,      -- 谁共享的
  folder_id INTEGER NOT NULL,     -- 他库里的哪个文件夹
  scope TEXT NOT NULL,            -- 'public'（全站）/ 'users'（指定人）
  created REAL, note TEXT
);
-- 指定人共享用现成的 folder_acl(owner, folder, grantee)
```

**注意**：共享的是**文件夹**，不是整个库 —— 这和项目主一贯的"按文件夹归类"习惯一致 ✓

### 4.4 模型与算力

| 东西 | 归属 | 说明 |
|---|---|---|
| 外部模型 API（地址/密钥/模型名） | **每人自己** | 存 `users/<id>/prefs.json`，**加密**；现在挤在全局 `meta` 里必须搬走 |
| 服务器本机模型（对话/VL） | **共用一台机器的** | 一个进程装一份，多人排队（已有 `gpu_slot` 机制可直接复用） |
| 嵌入模型（必须的） | **共用** | 每用户库里维度可以不同，但编码器只有一套 |

### 4.5 外网发布

```
公网 → 反代（Caddy，自动 HTTPS）→ 127.0.0.1:8199
```

必须一起做的四件（少一件就会出事）：

1. **TLS**（Caddy/Let's Encrypt，别裸奔 HTTP）
2. **注册开关**（管理员界面一键关，默认关）
3. **审核流**：注册 → `users.state='pending'` → 管理员通过才能登录（`users.state` 已经有这一列了 ✓）
4. **限流 + 防爆破**：`auth.py` 已有登录限流，但要扩到注册接口和 API

## 五、分阶段路线（建议按这个顺序，别跳）

### 阶段 0：地基（估 3~5 天）

- 库路径从"单库"改成"按用户选库"：`store` 由工厂按 `user_id` 返回不同实例
- **偏好搬进 `users/<id>/prefs.json`**（含模型密钥，加密）
- 迁移工具：把现有单库拆成 `shared/index.db`（owner_id=0 的部分）

**验收**：两个账号登录，各自的模型设置互不影响；A 看不到 B 的库文件内容。

### 阶段 1：共享语义 + 联邦检索（估 1 周）

- `shares` 表 + 共享/取消共享的接口和界面（文件夹设置里加「共享给…」）
- 检索/问答按"我的 + 共享给我的 + 公共"聚合，来源标注归属
- 权限贯穿：预览、下载、问答引用都要过同一道校验

**验收**：A 共享「相册」给 B → B 登录后能搜到、能预览、能看到来源；B 搜不到 A 没共享的文件夹。

### 阶段 2：替换同步机制（估 1~2 周，**最难也最危险**）

- 同步单元从"整库"改成"**我的文件夹**"：
  - 本机端：打包 `folders` 下指定 folder 的 files + chunks + 状态
  - 服务端：落到 `users/<id>/index.db`，**按内容哈希去重**、按 `updated_at` 取新
  - 冲突：**并集语义**（不删账号、不删文件夹、不改 path —— 和现有铁律一致）
- 本机版加「服务器地址自定义」＋「只同步这几个文件夹」＋「同步进度/失败重试」

**验收**：A、B 同时从各自本机推各自文件夹，服务器上两个库都完整，互不覆盖。
（这一步没走通之前，**不要**让两台机器同时推同一份库）

### 阶段 3：外网 + 注册审核（估 3~5 天）

- 反代 + HTTPS
- 注册开关（默认关）+ 审核队列 + 管理员通知
- 限流/审计（`auth.audit` 已有）

**验收**：公网域名访问、HTTPS 绿锁、注册需审核、未审核登录被拒。

### 阶段 4：体验与配额（可选）

- 每人的用量（文件数/片段数/存储）与配额
- 共享库的"订阅"（我关注谁的共享）
- 本机版一键"推送/拉取某个文件夹"

## 六、风险与取舍（这几条比功能更重要）

| 风险 | 说明 | 建议 |
|---|---|---|
| **同步和拆库必须同时改** | 如果先拆库、还用整库推送 → 一推就把别人的库盖掉，**不可逆** | 先做阶段 0 的"按用户选库"，**紧接着** 做阶段 2 的按文件夹同步；中间不要开放多人同时推库 |
| `meta` 全局偏好是**现存的多人问题** | 今天两个人的模型密钥就会互相覆盖 | 不管做不做大框架，**这条都该先修**（阶段 0 的第一件事） |
| 服务器没有 GPU | 服务器上跑不了本机视觉模型/嵌入，只能 CPU | 服务器定位"共享与检索"，**重活留在各人本机**；服务器本地模型只做文本 |
| 隐私文件夹的"不外发"要升级 | 外网之后，风险从"发给外部 API"变成"公开可访问" | 隐私标记要和共享发布**互斥**（隐私文件夹不给共享）；日志里不记正文 |
| 一人一库的检索会变多库 | N 个库并发查，N 大了会慢 | 先设个上限（比如同时最多查 10 个共享源），超了按分数截断 |
| 备份要跟着改成"按库" | 现在备份的是单库 | `dbbackup.py` 已经按"文件"做增量，多库只需循环调用（几乎不用改） |

## 七、我建议的第一步（今天就能做，风险最低）

**只做「每用户独立偏好」这一件事**，理由：

- 它**不依赖**拆库，改动面小（`meta` → `users/<id>/prefs.json`，读写各改一处）
- 它**现在就疼**：多人用会互相覆盖模型设置和密钥（这是现存 bug，不是未来需求）
- 它能验证"多人同时用"到底还有哪些地方假设了"只有一个用户"

做完这一步，再决定要不要继续走阶段 1（共享 + 联邦检索）——
那时候你对"多人到底怎么用"会有更真实的判断，比现在拍板更稳。

## 八、关于"网页端使用各自本机服务"的两种理解

| 理解 | 含义 | 成本 |
|---|---|---|
| **A. 数据服务**（我按这个写的方案） | 网页端能用到"我本机同步上去的知识库"，和"别人共享出来的库" | 就是阶段 0~2，**推荐** |
| **B. 算力节点** | 网页端把"嵌入/OCR/打标"这些重活塞给**你本机的显卡**去跑 | 要 WebSocket 长连接 + 任务队列 + 断线重试 + 安全鉴权，**多 2~3 周**，且本机关机就不可用 |

如果你的真实意图是 B（比如想用本机的 8G 显卡替服务器干活），告诉我，方案要另起一版——
但**建议先做 A**，A 做完再评估 B 是否真有必要。
