# 交接说明 · 多人版阶段 0（2026-10-20）

## 〇、先看这条：项目主定的架构（2026-10-20 晚）

> **服务器 = 共享主库 + 索引共用；隔离的是「归属和可见性」，不是物理分库。**

| 项 | 定调 | 现状 |
|---|---|---|
| 数据库 | 不分库，一个主库大家检索同一份索引 | ✓ 本来就是这样 |
| 隔离 | `folders.owner_id` + `visibility` + `folder_acl` | ✓ 已有 |
| 索引 | 共用；服务器上只有管理员能建（以建库机为权威），本机各管自己的 | ✓ 已实现（`/api/index/start` 里 `_can_index_here()`） |
| 打标 | 挂主库，默认只有管理员可用 | ✓ `start/pause/resume/stop/file-model` 全是 `_need_admin` |
| 备份 / 快照 | 同上，管理员专属 | ✓ 全部 `_need_admin` |
| 模型 API | 管理员设的 = 所有人默认；用户可自己覆盖 | ✓ 本轮做完（第二节） |
| 个人爱好 | 折叠 / 标签页 / 视图，永远只写自己 | ✓ 本轮做完 |
| 本机版 | 个人专用（单人多机），不做多人隔离 | ✓ 无改动 |

所以**不拆库**、**不做"对象级同步"**——最初方案里那两步作废。
真正剩下的活是：把"共享/私有"的语义打磨好 + 外网与注册审核。

## 一、第一步：界面偏好按用户存（已完成 ✓）

### 偏好分两层（项目主 2026-10-20 定的规矩）

| 类型 | 包含哪些键 | 管理员改 | 普通用户改 |
|---|---|---|---|
| **系统设置** | `eg2-rm*`（外部问答模型：url/key/model/hdr/apilist）、`eg2-vl*`（打标模型）、`eg2-kb*`（检索引擎）、`eg2-ignore*`（排除目录）、`eg2-backup*`、`eg2-snap*` | **同时写全局默认**（所有人没设过时用的那份） | 只写自己的（各自用各自的 API ✓） |
| **个人爱好** | `eg2-fold-*`（折叠）、`eg2-tab`（上次标签页）、`eg2-pgfold-*`、`eg2-pdf-view`、`eg2-pdf-fit` | **只写自己**，绝不推给别人 | 只写自己 |

没匹配上的一律按"个人"处理（安全：免得误改全局）。
判断在 `app/filesearch.py::_is_system_pref()`，接口返回里带 `global: [...]` 便于排查。

### 问题（不是未来需求，是现存的 bug）

`meta` 表只有 `(key, value)` 两列，41 个 `ui_pref.*` 全挤在这一份里。
两个人在同一台服务上用过界面，**后设的人会把前一个人的模型密钥、打标模型、
备份目录一起覆盖掉** ✗

### 做法

新增一张表（`app/store.py` 的 SCHEMA）：

```sql
CREATE TABLE IF NOT EXISTS user_prefs(
  user_id INTEGER NOT NULL,
  key     TEXT NOT NULL,
  value   TEXT,
  PRIMARY KEY(user_id, key)
);
```

语义是 **"全局默认 + 自己的覆盖"**：

| 读取情形 | 结果 |
|---|---|
| 没登录 / 后台任务（`user_id=0`） | 只读 `meta` 里那份**全局默认**（和以前完全一样 ✓） |
| 普通用户登录 | 全局默认打底，再用 `user_prefs` 里他自己的那几行盖上去 |
| 某人删掉自己的某项 | **只删自己的行**，不动全局、不动别人的 |

对应的方法（都加了 `user_id` 参数，默认 0 → 老调用点行为不变）：
`store.prefs_all(user_id)` / `prefs_set(key, value, user_id)` / `prefs_delete(key, user_id)`

接口（`app/filesearch.py`）：
- `GET /api/ui-prefs` → 按 `eg2_sid` 认人
- `POST /api/ui-prefs` → 写进当前用户名下，返回里多了 `scope: "user" | "global"` 便于排查
- 内部 `_pref_uid(request)` 是唯一的"该用谁的偏好"入口

### 验证

`run\check_user_prefs.py` **13/13 通过**（真发请求，用管理员 + 普通用户「张三」）：

- 两人设同一个键 `eg2-rmmodel` → 各自读回自己的，**互不覆盖**
- 打标模型 `eg2-vlmodelname` 同样互不影响
- 普通用户删掉自己那份 → 回落到全局默认，**管理员的没被连带删**
- 全程 `meta` 里的全局值一个字节都没变
- 测完自动清空 `user_prefs`、删掉临时会话，不留垃圾

## 二、第二步：按用户挑库的地基（已完成 ✓，行为不变）

### 做法：惰性启用

`app/userdb.py`（新文件）只做一件事——**"这个用户该用哪个库文件"**：

```
data/users/<用户id>/index.db 存在  →  用他自己的
不存在（现在就是这种情况）        →  回落主库 data/index/index.db
```

所以今天**跑起来和以前一模一样**（`split=false`），但以后把用户库建出来，
请求路径不用改就能各用各的 ✓

关键函数：

| 函数 | 作用 |
|---|---|
| `db_path_for(cfg, uid)` | 该用哪个库文件（唯一的判断入口） |
| `store_for(cfg, uid)` | 拿该用户的 `Store`，**LRU 最多同时开 4 个**（每个实例一份连接 + FTS 状态，不能全开） |
| `is_split(cfg, uid)` | 这个用户是否已独立成库 |
| `status(cfg)` | 给管理界面看：谁独立了、谁还在主库、当前开着哪几个 |

配套改动：`Store.__init__(self, cfg, db_path=None)` —— 不传就是 `cfg.db_path`，
**所有现有调用点零改动**。

只读诊断接口：`GET /api/admin/user-dbs`（管理员）

```json
{"split": false, "users": [], "opened": [], "max_open": 4,
 "main_db": "D:\\lingxi\\data\\index\\index.db"}
```

### 已知限制（下一步）

1. **检索目前只查一个库**。真正的多人要"我的库 + 共享给我的库 + 公共库"
   做联邦查询 —— 这是阶段 1 的核心工作量。
2. **后台任务没有"当前用户"概念**（打标 / 索引 / 备份），仍然用主库。
   多人化后要改成"任务归属于发起人"。
3. 前端 `localStorage` 仍是**浏览器级**的（多账号在同一浏览器会串味），
   服务端已经按用户存了，前端读取优先级还需要调整。
4. 管理员的偏好写进他自己名下，**不会自动变成"大家的默认"**。
   如果需要"管理员改的就是全局默认"，要另外加一个「应用到所有人」的开关。

## 三、运行形态：个人版 / 管理员版 / 成员版（已完成 ✓）

项目主 2026-10-20："本地版是希望个人专用（应该有管理员版可以统管全局，与个人版区别）"

**同一套代码，三种形态**，由 `/api/folders` 返回的 `view_mode` 决定界面长什么样：

| 形态 | 什么时候是它 | 能看到什么 |
|---|---|---|
| `personal` **个人版** | 本机（`run/deploy/sync_db.py` 存在 = 建库机） | 索引、打标、备份、快照、隐私文件夹全有；**没有"用户管理 / 共享设置"** |
| `admin` **管理员版** | 服务器 + 管理员登录 | 上面全部 **+ 用户管理 + 共享设置**（统管全局） |
| `member` **成员版** | 服务器 + 普通用户 | 只有问答、搜索、自己的人物页；管理类卡片全隐藏 |

实现：
- 后端 `_view_mode(role, can_index)` 是**纯函数**，调用方传角色进来
- 前端 `applyViewMode(mode)`：带 `data-view="personal admin"` 的卡片按形态显隐；
  带 `data-admin-entry` 的入口只在 `admin` 出现
- 已标记的卡片：`cpq-card`（PDF 打标）、`snap-card`（快照）、`priv-card`（隐私文件夹）、
  `bk-card`（定时备份）、`progress-card`（索引状态）

> ⚠ **踩坑**：最初 `_view_mode` 自己去调 `_who(request)`，而 `_who` 是 `create_router()`
> 里的**闭包函数**，模块级根本看不见 → `NameError` 被 `except` 吞掉 → 服务器上
> 管理员也判成"成员版" ✗。改成纯函数、由调用方传角色才对。

### 为什么不做成两个安装包

一套代码少一半维护量，升级不用装两次。要区分的地方只有"界面显示什么"，
后端权限本来就有（`_need_admin`），所以用 `view_mode` 控制展示就够了 ✓

## 四、权限矩阵：本机 vs 服务器（2026-10-20 定稿）

项目主原话：
> "普通用户应该能备份还原**他本机**的，只是不能操作服务器，这个要区分"
> "成员个人版应该在他本机上能建库索引打标及设置个人API等，要不如何建自己的库"
> "用户也应该在服务器上自己设自己的API"

**判据是「这台机器是不是他自己那台」，不是「他的角色是什么」** —— 见
`app/filesearch.py::_need_admin_or_local()`：

```python
if _can_index_here():      # 本机（建库机）→ 登录即可：这台就是你的机器
    return u
if u["role"] != "admin":   # 服务器 → 必须管理员
    raise HTTPException(403, "…请在自己电脑上打开本机版 ✓")
```

| 能力 | 本机（普通用户） | 服务器（普通用户） | 服务器（管理员） |
|---|---|---|---|
| 建库 / 索引 | ✓ 只能动自己的文件夹 | ✗ 403 | ✓ |
| 打标（含设单文件模型） | ✓ | ✗ 403 | ✓ |
| 备份 / 还原 / 拍快照 / 同步到移动硬盘 | ✓ **自己那台的数据** | ✗ 403 | ✓ |
| 改快照同步目标 | ✓ | ✗ 403 | ✓ |
| 设自己的模型 API | ✓ | ✓（写自己名下） | ✓（同时成为全局默认） |
| 个人爱好（折叠/标签页/视图） | ✓ | ✓ | ✓ |
| 用户管理 / 共享设置 / 跨用户信息 | — | ✗ | ✓ |

## 五、本机 → 服务器 上传通道（已完成 ✓）

项目主："每人各自管理各自文件、上传同步进服务器"

### 为什么不是"整库推"

`run/deploy/sync_db.py` 是**整库覆盖**，适合"一台机器就是全部数据"。多人以后
A 推一次就会把 B 的东西整个盖掉 ✗。所以新通道是**按文件夹打包**，服务器收到后
按 path **并集**合并，归属记成上传者 ✓

### 三个新接口（`app/filesearch.py`）

| 接口 | 谁能用 | 干什么 |
|---|---|---|
| `POST /api/sync/folder-upload` | **登录即可**（每人传自己的） | 收包 → 合并进主库，`dry_run=true` 只统计 |
| `GET /api/sync/export` | 登录 | 把本机文件夹打包（普通用户只导自己名下的） |
| `GET /api/sync/download` | 登录 | 下载刚打的包（只认临时目录里的 `eg2-export-*`） |

### 搬运模块 `app/foldertransfer.py`

JSONL + gzip，四种记录：`meta` / `folder` / `file` / `chunk`，向量用 base64。

⚠ **别和 `app/foldersync.py` 搞混**：那个管"`visibility`/`owner_id` 这些**设置**
在两边怎么合并"；这个管"文件夹里的**数据**（文件、片段、向量）怎么搬"。

三条硬规矩（都是踩过的）：

1. **不按 id 搬** —— id 是各库自己的自增，跨库必然撞。全程用 `path` 做稳定键。
2. **维度必须一致** —— 老数据里有 256 维的 chunk，导进 768 维的库会让搜索结果错乱
   → 不一致的**跳过并计数**，绝不硬写。
3. **不覆盖 path、不覆盖已有设置** —— 同 path 的文件夹已存在时，只补**缺失**的配置键。

另外 `ensure_cols()` 会在导入前补齐 `owner_id` / `visibility` / `privacy` 这些
"多人迁移才加的列"（往新建的空库导入时它们还不存在）。

### 本机怎么用

```powershell
# ① 先预演（服务器不写库，最安全）
& .\venv\Scripts\python.exe -u run\upload_folders.py --dry-run

# ② 真传（默认传"我名下的全部"，也可以指定）
& .\venv\Scripts\python.exe -u run\upload_folders.py
& .\venv\Scripts\python.exe -u run\upload_folders.py --folder-ids 36,88

# 服务器地址改 config.ini 的 [sync] server（也可以 --server 临时指定）
# 登录：--token（浏览器 Cookie 的 eg2_sid）或 --user 名字 --password 密码
```

### 验证

| 脚本 | 验什么 | 结果 |
|---|---|---|
| `run\check_foldertransfer.py` | 导出/导入往返（临时库，不碰主库） | **22/22** |
| `run\check_upload_e2e.py` | 本机打包 → 真 POST 到服务器 → 服务器解析（预演） | **8/8** |

`check_foldertransfer.py` 里几条关键的：导进空库后**数量与原库一致**、向量不是空壳
（长度 = 维度×4）、**再导一次不重复**、维度不一致的**被跳过**、同 path 的文件夹
**不覆盖**我原来的设置、`owner_id` **记成上传者**。

> ⚠ 又踩一个：`/api/sync/export?folder_ids=-1` 这种非法值解析不出 id，
> 结果落进了"不传就导全部"的分支，**一口气打了 121 MB 的整库包** ✗
> 已改成"传了但解析不出来就报 400"，绝不偷偷导出整库。

## 六、本机界面上的「⬆ 上传到服务器」（已完成 ✓）

命令行能用之后，又补了界面（项目主："按你建议继续"）。

### 卡片长什么样（⚙ 设置页）

```
⬆ 上传到服务器                                    就绪
把你这几个文件夹的文件 + 片段 + 向量打包送到服务器。服务器按路径合并
（只增不删，不会盖掉别人的东西），归属记成你本人 ✓
第一次建议先点「预演」：服务器只统计、不写库。

[http://192.168.1.10:8199] [服务器账号] [密码（留空=不改）] [保存]
服务器：http://192.168.1.10:8199 · 账号 yqdnsjs · 密码已保存
┌────────────────────────────────────────────┐
│ ☑ \\NAS\photo\证件          7 个文件   │  ← 可滚动
│ ☐ D:\notes\wechat               120 个文件  │
└────────────────────────────────────────────┘
[全选] [清空]                    [🔍 预演] [⬆ 上传]
```

- **预演**：走完打包 + 登录 + 上传，但服务器 `dry_run=true` 不写库 → 先看会新增多少
- **上传前二次确认**，上传过程中有进度条（按已发字节算百分比）
- 结果直接显示服务器返回的统计（新建/命中的文件夹、文件、片段数）

### 三个接口

| 接口 | 作用 |
|---|---|
| `GET /api/sync/push/status` | 状态 + `can_push` + 账号信息（密码只回 `has_password`/`has_token`） |
| `PUT /api/sync/account` | 存服务器地址 / 账号 / 密码 / token（地址必须带 `http://`） |
| `POST /api/sync/push` | 后台开始推（`dry_run=true` 预演），进度靠 status 轮询 |

界面每 3 秒轮询一次进度；**服务器上这个卡片会自动消失**（`can_push=False`，
它本来就是接收端）。

凭据有两种给法：**账号 + 密码**（推送时现登录，token 不落盘），
或者**直接填 token**（浏览器 Cookie 里的 `eg2_sid`；本机与服务器同步过同一份库时，

## 十一、维度不同能不能上传？（2026-10-21 结论：**能**）

项目主追问："用户能用不同维度建库上传吗？"

### 结论：能，而且本库一直是混合维度

```
本机库：256 维 41207 条 + 768 维 21603 条，同时存在
#36 obsidian     768 维 13592 条      #44 手机同步上传   256 维 10746 条
#77 Shared      768 维  5727 条      #48 TEMP          256 维  6585 条
```

`store._load_matrix()` 的做法是**按 dim 分组**，查询时"把查询向量按各分组的维度切片"，
所以不同维度的片段**本来就能一起搜** ✓

### 差点犯的错（值得记）

第一次做上传时我加了"维度不一致就跳过"，想的是"防止污染"。
实测把一个 768 维文件夹（#36，21179 条片段）传到 256 维的服务器：

| 版本 | 结果 |
|---|---|
| 跳过版（错） | `skipped_dim = 13592` → **用户传上来的数据全被扔掉**，"能上传但用不了" ✗ |
| 现在（对） | `skipped_dim = 0`，**21179 条全部进库** ✓ |

**"跳过"比"写进去"更糟**：写进去至少能搜到，跳过等于用户白发一次上传。

所以 `import_pack()` 默认 `strict_dim=False`（照收）；`expected_dim` 只用来
**算提示**（服务器 X 维、你这包 Y 维），不再当"扔数据"的依据。

### 现在的提示是"建议"不是"错误"

- 维度不同 → 黄色 💡：**能用**，但统一成服务器那个维度更省空间、检索更快
- 维度相同 → 绿色 ✓

统一维度的办法：本机把该文件夹的维度改成服务器的值 → 重建索引 → 再上传。

### 验证

`run\check_dim_mismatch.py` **6/6**（真上传一个 768 维文件夹到 256 维服务器）：

```
本地维度 768 / 服务器 256 / dim_ok=False / 跳过 0 条
★ 一条都没跳过（不同维度照收）      skipped_dim = 0
★ 片段照样全部能进库                新建 21179 / 命中 0
```

## 十六、真 bug：共享了但用户用不了（2026-10-21 修）

项目主："我共享了相册与文件夹的，用户不能用吗"

### 症状

管理员把 #36（obsidian）、#88（灵犀知识库）都设成了**共享**，也都开了「作为知识库」，
自己问答一切正常；普通用户「张三」一问就报"当前账号没有可用的知识库文件夹"。

### 根因

`app/multiuser.py::visible_folder_ids()` 里那条规则是：

```python
elif owner == 0 and vis == "shared":    # 只有"无主"的共享库才算公共
    out.append(fid)
```

可是 **2026-10-21 凌晨刚把所有文件夹的 `owner_id` 从 0 改成了管理员(3)**
（那一轮"把现有文件数据全归为现有管理员"）——
于是所有 `shared` 文件夹的 owner 都变成了 3，**不再满足 `owner == 0`**
→ 对普通用户全部不可见 ✗

管理员看自己是"不限制"（直接返回 None），所以**只有普通用户能感觉到**，
而且报错文案还是"请让管理员把知识库设为共享"——管理员一看"我明明设了"，
互相怀疑，极难定位。

### 修法

```python
elif vis == "shared" and (uid or owner == 0):
    # 登录用户：所有 shared 都可见（不管 owner 是谁）✓
    # 匿名(uid=0)：仍只看 owner=0 的公共库（保持原来的防泄漏行为）✓
    out.append(fid)
```

### 验证

`run\check_visibility_rules.py` **9/9**（守住四条，防止放宽过头）：

| 规则 | 结果 |
|---|---|
| 自己的私有 → 可见 | ✓ |
| **别人的 shared → 登录用户可见**（这次修的） | ✓ |
| 别人的 private → **不可见** | ✓ |
| `folder_acl` 点名 → 可见 | ✓ |
| 匿名 → 只看 owner=0 的公共库（看不到别人的 shared/私有） | ✓ |
| 管理员 → 不限制 | ✓ |

修完服务器实测：

```
普通用户「张三」可见文件夹 16 个（含 #36、#88）
可写文件夹：只有 #108（他自己那个）
→ 他能问答用的知识库：2 个 ✓
```

## 十七、共享的人脸 / 人物：普通用户只读（2026-10-21）

项目主："服务器用户应该不能改共享的人脸和重命名吧，这个也要修"

### 结论：后端本来就没漏，漏的是**界面没告诉用户**

`_need_people_write()` 的规则是"**整组的脸都得在我能写的文件夹里**"，
`_need_face_write()` 是"这张脸所在文件夹归我"。实测全部拦住：

| 试什么 | 结果 |
|---|---|
| 重命名共享文件夹里的人物 | **403**，名字没变 |
| 改共享文件夹里那张脸的归属（`DELETE /api/faces/{id}/person`） | **403** |
| 删共享文件夹里的脸（`DELETE /api/faces/{id}/drop`） | **403**，脸还在 |
| 合并人物（`POST /api/people/people-merge`） | **403** |

但 `GET /api/people` **没告诉前端**"这个人物我能不能改"，
所以人物卡片上的「⋯（整组/命名）」和「换（换头像）」按钮**全是亮的**，
点了才吃 403 —— 用户会觉得"明明能点，为什么不行" ✗

### 改了什么

1. **后端** `GET /api/people` 每个人物多一个 `writable`：
   规则和 `_need_people_write` 一致（涉及的所有文件夹都在我可写范围内）。
   一次查完 `(人物 → 文件夹)` 映射，不按人物逐个查（123 个也很快）。
2. **前端** 人物卡片：
   - `p.writable === false` → 「⋯」和「换」按钮 `disabled` + 半透明 + 悬停说明
     "这个人物在共享文件夹里，只有管理员能改"
   - 卡片点击（未命名→命名）也打 `data-ro="1"` 标记，不再触发命名

### 验证

- 本机 `run\check_people_readonly.py` **6/6**
- 服务器 `run\deploy\check_people_server.sh` **5/5**：

```
人物 123 个，带 writable 字段 123 个，其中可改 0 个
★ 重命名只读人物被拒（403）  HTTP 403
★ 名字没被改动  张三
★ 前端有 canEdit 置灰 / 按钮 disabled 逻辑在
```

（"可改 0 个"是**对的**：张三名下只有 #108 一个文件夹，而那些人脸都在共享文件夹里。）

> ⚠ 这轮踩的：测 `/api/faces/{id}/person` 时我先写 POST 再写 PUT，都是 **405**，
> 一度以为"没拦住" ✗ 实际它是 **DELETE**。

## 二十三、聊天里漏出管理员 API（2026-10-22 修，两个 bug 叠加）

项目主："服务器版上聊天模型又出现了管理员api的模型"

### bug ①：`prefs_all()` 用了默认参数

`chat_api.py` 里几处：

```python
prefs = store.prefs_all(uid)        # ← 默认 inherit_sensitive=True，会继承全局 ✗
```

之前只把 `/api/ui-prefs` 改成了按角色传参，**新写的聊天模块没跟上** ✗
→ 普通用户在服务器上打开聊天，模型下拉里是管理员的 API 列表。

修：统一走 `_prefs(request)`，内部按 `role == "admin" or _local()` 决定要不要继承。

### bug ②：`chat2` 没注册 `dbreload`

排查时发现服务器上**管理员也是 0 个模型**，日志里有：

```
WARNING eg2.chat2: 列 API 配置失败：Cannot operate on a closed database.
```

`create_router(cfg, store, engine)` 把 `store` 闭包捕获了，而服务重启 / 换库时
旧连接会被关掉。`filesearch` 和 `settings_api` 都注册了 `dbreload` 回调来重绑，
**chat2 漏了** ✗ → 重启后所有聊天接口读的都是已关闭的连接，
而且被 `except` 吞掉 → **静默返回空**（最难查的那种）。

修：注册 `dbreload`，换库时把 `store` 和缓存的 `searcher` 一起重置。

> 这个 bug 其实"帮了倒忙"：它让管理员也看不到模型，反而掩盖了 bug ①
> —— 两个 bug 叠在一起，表面现象是"谁都看不到"，实际是一个泄漏 + 一个空列表。

### 验证（`run\check_chat_cred.py`，服务器上跑）

```
管理员：2 个（云端 opencode / 本地 llama.cpp）✓
普通用户：0 个 ✓
普通用户自己配了 → 只看到自己的 1 个 ✓
通过 6 项，失败 0 项
```

> ⚠ 本机跑这个脚本会"失败"（普通用户也能看到管理员的），那是**正确的**：
> `_local()` 为真 = 这台机器是他的，配置不隔离。所以这个脚本要在服务器上跑才有意义。
