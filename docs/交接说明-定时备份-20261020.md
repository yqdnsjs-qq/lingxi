## 一、这是干什么的（项目主原话）

> 「把最重要的定时备份数据库功能补上，本地与服务器上都做，是不是可以双重保证？
> 最好是增量备份，不希望浪费硬盘容量，而且要自定义的备份数量保证（比如我要求
> 10 份，就是保存最新 10 份，循环替换旧备份，但要有自定义固定备份功能（不被替换））」

翻成四件事：

| 要的事 | 怎么做的 |
|---|---|
| 定时备份 | 本机 Windows 计划任务 + 服务器 crontab，都是**每 30 分钟叫醒一次**，真正存不存看间隔（默认 6 小时）|
| 本地 + 服务器双份 | 两边各跑一份，各自的库各自留历史（本机硬盘坏了有服务器那份，反之亦然）|
| 增量、不浪费硬盘 | **页级差异**：只存这一版变动过的 4 KB 页。实测增量 **0.04~0.07 MB**，而全量是 443 MB |
| 份数可自定义 + 固定份 | `config.ini` 的 `[backup] keep`（默认 10），轮换只删最旧的；标了 📌 的**永不删除** |

实测账（2026-10-20，库 443 MB）：

```
1 份全量 + 2 份增量  = 444.8 MB
若每份都存全量        = 1329 MB
```

## 二、怎么用（都是现成的，不用改代码）

### 本机

```powershell
# 看状态（几份、占多大、上次什么时候、下一份该不该做）
& .\venv\Scripts\python.exe -u app\dbbackup.py status

# 立刻存一份（没变化会自动跳过，不写盘）
& .\venv\Scripts\python.exe -u app\dbbackup.py save "手工备份：调完索引"

# 固定某一份（📌 轮换时永不删）／取消固定
& .\venv\Scripts\python.exe -u app\dbbackup.py pin 20261020-031650
& .\venv\Scripts\python.exe -u app\dbbackup.py unpin 20261020-031650

# 校验某一份（重建到临时文件 + 比 sha256，确认"真能恢复"）
& .\venv\Scripts\python.exe -u app\dbbackup.py verify 20261020-031650

# 立刻按份数轮换
& .\venv\Scripts\python.exe -u app\dbbackup.py prune
```

界面：**设置页 →「💾 定时增量备份」卡片** —— 开关、保留份数、间隔小时、
立刻备份、按份数轮换、每份的 📌 固定 / 校验能恢复，全在里面。

计划任务（已经注册好，重装系统后要重跑一次）：

## 三、原理（为什么能省 99%）

SQLite 的库是**定长页**拼起来的（本库 `page_size = 4096`，约 10.8 万页）。备份时：

1. 用 SQLite 官方**在线备份接口**做一份一致性快照（服务开着也安全，不用停服）
2. 把快照按页切开，逐页算 8 字节摘要（blake2b）
3. 和**上一份备份**的摘要表逐页比 → 只有变了的页要存
4. 存成 `patch.z`（页号表 + zlib 压缩的页内容）

恢复 = 从最近的**全量**开始，把每份增量里的页**按页号覆盖**上去，最后按当时的
文件长度截断 → 与当时那份快照**逐字节一致**（`verify` 就是拿 sha256 卡这个）。

目录长这样：

```
backups\db\
  20261020-031047\
      meta.json     类型/父份/页数/长度/sha256/固定标记/说明
      full.db       全量时的完整快照
      patch.z       增量时的变化页
      pages.bin     这一份的逐页摘要表（下一份拿它比）
  20261020-031211\ …
  last.json         上次检查 / 上次真正存盘的时间
```

**没有变化就不落盘**：内容与上一份完全一致时只更新 `last.json`，不占空间 ✓

## 四、轮换与固定（最容易踩的地方）

- 保留 `keep` 份**未被固定**的；固定份不占这 10 个名额，也不参与删除
- 删除前一定会**先保证留下来的链是完整的**：谁的父份要被删掉，就先把谁
  **重建为新的全量**，然后才删旧份
- 所以任何时刻，每一份都能独立恢复（`verify` 会逐个卡）

> ⚠ **踩过的坑（重要）**：第一版只把"剩下的最早一份"提升为全量 ✗。
> 结果「固定份夹在链中间」时就断了 —— 实测 A(固定·全量) → B → C，删 B 之后
> C 报 `备份链断了：找不到父份 B` ✗。
> 必须**逐个检查"父份还在不在"**，不在就提升它自己 ✓（自测脚本第 ⑦ 项就是卡这个）

## 五、恢复演练（真要还原时照着做）

```powershell
# ① 停服务（还原时库不能被占用）
& .\stop.bat        # 或 run\restart_server.py 的停止部分

# ② 先确认这份真能恢复（不写任何东西）
& .\venv\Scripts\python.exe -u app\dbbackup.py verify 20261020-031650

# ③ 还原到线上库（会自动把现有库另存 index-before-restore-*.db）
& .\venv\Scripts\python.exe -u app\dbbackup.py restore 20261020-031650 --to data\index\index.db

# ④ 起服务
& .\venv\Scripts\python.exe -u run\restart_server.py --no-ui
```

也可以先还原到**别的文件**再慢慢看：

```powershell
& .\venv\Scripts\python.exe -u app\dbbackup.py restore 20261020-031650 --to D:\tmp\check.db
```

> ⚠ 老的 `backup.bat`（`app\backup.py`，整库全量）**没有删**，两套并存：
> 它胜在简单直白（一份就是一个 `.db` 文件，随便拷走就能用），
> 新的这套胜在省空间和自动化。要长期保留的关键版本，建议**用新套的 📌 固定**，
> 或者同时留一份 `backup.bat` 的全量。

## 六、配置（`config.ini` 的 `[backup]` 段）

```ini
[backup]
enabled = yes          ; 总开关（no = 定时任务什么都不做）
dir = db               ; 逻辑子目录（相对项目 backups\）
interval_hours = 6     ; 多久存一份（小时）
keep = 10              ; 保留多少份（不算固定份）
```

改完**立刻生效**（界面保存走 `PUT /api/backup/settings`，服务会 `cfg.reload()`），
不用重启。

接口（都要管理员，除了 status）：

| 端点 | 作用 |
|---|---|
| `GET /api/backup/status` | 份数/占用/上次检查/该不该做 |
| `POST /api/backup/run` | 立刻存一份（无变化则跳过） |
| `POST /api/backup/pin` | `{stamp, pinned}` 固定/取消固定 |
| `POST /api/backup/prune` | `{keep?}` 立刻轮换 |
| `POST /api/backup/verify` | `{stamp}` 重建校验 |
| `PUT /api/backup/settings` | `{enabled?, interval_hours?, keep?}` |

### 这一轮踩的坑（省得再踩）

| 现象 | 真因 | 修法 |
|---|---|---|
| 增量一存就是 202 MB（108146 页，全库） | 比较时要求"两次页数必须相等"才逐页比，库一增长就退化成全存 ✗ | 按页号逐个比，旧表不够长就当新页 ✓ |
| 轮换后报 `备份链断了：找不到父份` | 只把"剩下的最早一份"提升为全量，固定份夹在中间时后继者仍指向被删份 ✗ | 逐个检查"父份还在不在"，不在就把它自己提升为全量 ✓ |
| `Register-ScheduledTask` 报 `Access is denied` | 走 CIM 的注册被这台机器拒绝（和 `setup_task.py` 踩的是同一个） | 回落到 `schtasks /Create` ✓ |
| `pythonw` 下什么都看不到 | `pythonw.exe` 没有控制台，print 无处可去 | `run\backup_db.py` 用 Tee 同时写 `logs\dbbackup.log` ✓ |

## 八、还剩什么（没做 / 要留意的）

1. **同秒重复触发**：份名后会自动加 `-2`、`-3`，但极少发生（10 分钟一次也叫不醒两次）
2. **服务器 backup 目录会跟本机一样涨**：库大了以后两边各留 10 份增量通常仍是几百 MB 级；
   若哪天库涨到几 GB，建议把 `interval_hours` 调大或 `keep` 调小（界面里就能改）
3. **`backups\snapshot-*`（源码快照）不归这套管**：那是每次改代码拍的整份源码，
   已经有 160 多份、占几十 GB，属于另一个话题，要清理得单独定规则
4. **没有做"备份到第三处"**：目前是本机 + 服务器两处；要再加，把 `dir` 指到
   NAS 挂载点即可（`[backup] dir = \\\\NAS\\share\\lingxi-db`），但增量目录要求能
   随机写、不能被同步工具挪动文件
