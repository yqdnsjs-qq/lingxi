## 一、它是什么

### 核心能力

| 能力 | 说明 |
|---|---|
| **模糊搜索** | 用自然语言描述找文件（"去年的报销发票"），支持语义 + 字面混合排序 |
| **景象搜图** | 搜"海边""生日蛋糕"，按画面内容找照片 |
| **人脸识别** | 自动检测照片里的人脸、聚类成人物、按人名筛照片 |
| **知识库问答** | 把 markdown 笔记/文档做成知识库，用本地小模型问答并给出来源引用 |
| **图片打标** | 用视觉模型给图片生成中文描述，让"图里的文字"也能被搜到 |
| **混合搜索** | 景象词 + 人名 同时筛选（"海边的李四"） |

### 技术栈

```
模型：google/embeddinggemma-2      740M 全模态嵌入（文本+图片+音频），768 维
      可选 Qwen2.5-1.5B/3B/Qwen3-4B   本地问答
      可选 Qwen2.5-VL-3B              图片打标
人脸：facenet-pytorch（MTCNN + InceptionResnetV1 vggface2，512 维）
运行：Python 3.12 + PyTorch 2.x + CUDA + FastAPI
界面：单页 HTML（暗色主题，五个标签页）
```

### 资源需求

```
显卡：8 GB 显存可用（RTX 3060 Ti 8GB 实测流畅）
磁盘：模型约 2 GB + 索引约 1 GB/万文件
系统：Windows 10/11（脚本用 .bat，Linux 需自己改启动命令）
```

## 二、部署：从零开始

### 前置条件

```
① Windows 10/11
② NVIDIA 显卡 + 驱动（建议 8 GB 显存以上）
③ Python 3.12（安装时勾选 "Add to PATH"）
④ 网络：能访问 pypi.tuna.tsinghua.edu.cn 和 modelscope.cn
   （huggingface.co 在国内不可达，本项目已全部改走 ModelScope）
```

### 步骤

```bat
:: 1. 把本项目放到一个没有中文和空格的路径，例如 D:\eg2
::    然后双击：

setup.bat
```

`setup.bat` 会自动完成：

```
① 创建项目内虚拟环境 venv\
② 装 PyTorch（CUDA 版，从清华镜像）
③ 装其余依赖（transformers / fastapi / pillow-heif / librosa / av / pypdf …）
④ 从 ModelScope 下载 google/embeddinggemma-2 模型
⑤ 生成默认 config.ini
⑥ 自检（selftest.bat）
```

**首次安装约 30-60 分钟**（取决于网速），主要是下载 PyTorch（约 2.5 GB）和模型（约 1.4 GB）。

### 安装人脸功能（可选）

人脸识别依赖 `facenet-pytorch`，它**故意不装进主 venv**，避免污染依赖：

```bat
:: 人脸权重需要手动下载（GitHub 在国内不可达）
:: 已包含在发布包的 face-lab\models\ 里，或从 ModelScope 获取
```

**如果不需要人脸识别**，在 `config.ini` 里设：

```ini
[face]
enabled = no
```

### 安装完成后的自检

```bat
selftest.bat
```

会检查：Python 环境、模型文件完整性、数据库、显存、端口占用。

## 三、启动与停止

| 脚本 | 作用 |
|---|---|
| **`start.bat`** | 启动服务并打开浏览器（默认打开搜索页）|
| **`search.bat`** | 同上（语义化名字，双击即用）|
| **`stop.bat`** | 停止服务，**并关掉界面窗口**（连命令行窗口一起关掉）|
| **`restart.bat`** | 重启（先停后启）|
| **`status.bat`** | 看服务状态、索引统计、显存占用 |
| **`backup.bat`** | 备份数据库 |
| **`安装PDF原版式.bat`** | 补装 PyMuPDF（让 PDF 能「看原版式」出图）。`setup.bat` 一般已经装好，只有旧环境或装失败了才需要它 |

界面的浏览器窗口由 `app\close_ui.py` 负责关闭：它按标题关键字找到那些窗口，
**先发关闭请求**（让浏览器有机会把界面设置写回磁盘），关不掉再强杀进程。
`start.bat` 在开新窗口之前也会先清一遍，所以反复启动不会留下一堆重复窗口。

**两个细节**（都踩过坑）：
- 服务已经在跑的时候双击 `search.bat`，它会**只打开界面窗口**，不会去杀正在跑的服务；
  只有确认服务没在跑才会清遗留的服务窗口。
- 服务那个黑框（标题「宇之语·灵犀 服务窗口」）是正常现象：运行日志写在文件里，
  窗口里几乎不输出东西，可以最小化，不用管它。**要停服务请双击 `stop.bat`**，
  别直接关黑框（直接关等于强杀，浏览器来不及把界面设置写回磁盘）。

**默认地址**：`http://127.0.0.1:8199`

### 关于开机自动扫描

```ini
[search]
auto_scan_on_start = yes    # 每次启动都做一次增量扫描
```

**注意**：增量扫描只比对「文件大小 + 修改时间」，所以很快。但如果加了新文件夹，第一次扫描会跑很久。

**想临时关掉**：把它改成 `no`，或启动后在界面上点「停止索引」。

## 四、五个标签页怎么用

### 🔍 搜索

```
[用自然语言描述你要找的文件…      ] [30条▼] [搜索]

[全部文件夹▼] [＋ 按人物筛选▼] [全部类型▼]   命中 30 个文件，用时 1.9 秒
```

**用法要点**：

```
· 描述得越具体越好："蓝色圆形的产品图" 好过 "产品图"
· 景象词 + 人名：搜索框填「海边」，人物栏选「李四」
     → 结果是「海边 + 有李四」的照片
· 「切换到图片墙」把结果铺成缩略图墙（图片类结果带缩略图）
· 结果卡片上的通道标记能验证匹配方式：
    [语义] 向量相似  [文字] 字面命中  [人物] 人脸命中  [文件名] 文件名命中
```

**PDF 预览**：顶部有三个切换 —— **内置查看器**（默认，原版式，可缩放）、
**按页文字**（标「第 N / 总页」，搜到的词在哪一页一目了然，命中页自动跳过去）、
**看原版式**（把那一页渲染成图片，表格线、合并单元格都在）。

**怎么知道搜到的东西在第几页**：预览 PDF 时，程序会拿查询词**去 PDF 的文字层里按字面找**，
找到就**默认直接显示「看原版式」**：整页缩放（一眼看到全貌）+ 命中位置用**黄框**标出来。

```
· 找到 → 顶部写「命中「某某」在第 N 页」，默认整页出图、黄框标住那几个字
        点页面图可以切换「整页（看全貌）↔ 适宽（看清小字）」
        切到「内置查看器」会直接跳到第 N 页，并按整页缩放显示（可自己缩放/选择文字）
        「按页文字」里会写「本页有 1 处」，翻到别的页还给了「跳到命中页」按钮
· 没找到 → 会明确写「页面上没有「某某」的字面文字（这条是语义命中）」
        —— 语义搜索命中的内容不一定逐字出现在页面上，这种情况不能硬说在哪
· 没有查询词（比如直接从文件夹点开 PDF）→ 提示「没有查询词，没法定位」
```

> 为什么黄框只能在「看原版式」里画：内置查看器是浏览器自带的 PDF 插件在渲染，
> 网页没法在上面叠东西；而「看原版式」的页面图是程序自己渲染的，想标哪就标哪。

定位和出图都是预览时现读的，不用重建索引；需要 PyMuPDF
（`setup.bat` 会装；没装的话预览里会提示，退出后双击 `安装PDF原版式.bat` 补装）。

**界面设置会自动记住**：卡片折叠状态、上次打开的标签页、列表/图片墙、排序方式、
外部模型配置这些，除了浏览器本地存一份，服务端（`data\index\index.db` 的 meta 表）
也存一份。所以即使 `stop.bat` 强杀浏览器窗口、或者浏览器缓存被清了，重新打开还是原样。

**人物页的分区可以折叠**：点「已命名 / 未命名」标题即可折叠/展开，状态同样会被记住。

## 五、文件夹与索引模式

每个文件夹可以单独设索引模式。添加文件夹时选一次，之后随时可改。

| 模式 | 索引内容 | 提人脸 | 适用 |
|---|---|---|---|
| **相册** | 只图片 | ✅ | 照片目录（不读正文，最快）|
| **文字 + 图片** | 正文 + 图片 | ✅ | 混合目录 |
| **全模态** | 文字+图片+音频+视频 | ✅ | 什么都想搜 |
| **仅文字** | 只正文 | ❌ | 文档目录 |
| **跟随全局** | 用 `config.ini` 的设置 | 看全局 | 默认 |
| **只索引文件名** | 只有文件名 | ❌ | 只是想让文件出现，最省 |

**关键**：**人脸提取和「索引图片内容」是同一个开关**。关了就不提人脸。

### 排除规则

每个文件夹可设排除规则（按扩展名 / 文件名 / 相对路径通配符）：

```
配置 → 排除规则，每行一条：
  *.tmp
  @Recycle
  .git
  */缩略图/*
```

**「预览排除效果」按钮**能先看会排掉哪些文件，确认后再生效。

### 增量更新 vs 重建索引

```
增量更新  → 只处理「大小或修改时间变了」的文件。日常用这个。
重建索引  → 忽略时间戳，全部重做。改了模式或怀疑索引有问题时才用。
            ⚠ 很慢，1 万张图可能十几小时
```

## 六、人脸识别工作流

人脸识别不是点一下就完事的，需要**人工整理几轮**。完整流程：

```
① 扫描照片（索引时自动提人脸）
      ↓
② 「重新聚类」→ 把所有人脸分成组
      ↓
③ 逐个命名
      · 点未命名的卡片 → 打开人脸墙 → 顶部输入名字 → 「命名这组」
      · 名字已存在时会提示合并（避免同名两组）
      ↓
④ 清理错误的
      · 整组是别人  → ⋯ → 合并到那个人
      · 整组是杂的  → ⋯ → 整组解散
      · 个别脸错    → 换 → 逐张「移除」（不是这个人）
      · 根本不是脸  → 换 → 逐张「非脸」（栏杆/花纹误检，彻底删除）
      ↓
⑤ 「同名去重」→ 合并所有同名组
      ↓
⑥ 「归类补全」→ 把剩下的脸补进已有的人
```

### 关于阈值

```
config.ini [face] 里的三个阈值：

assign_threshold = 0.78    归类补全用（调高更严，宁可少补不乱补）
search_threshold = 0.45    以图搜人用（调低召回更多）
cluster_threshold = 0.75   重新聚类用（界面上也能调）

实测参考：同一个人中位数 0.88，不同的人中位数 0.32
```

**界面上可以直接调聚类阈值** —— 「人物」工具栏的 `阈值 [0.75]` 输入框，改完点「重新聚类」立刻看效果。

**调高** → 组更纯但同一个人会被拆成几组（用「同名去重」合回来）
**调低** → 组更大但容易混人

### 重要：重新聚类不会丢名字

```
「重新聚类」的行为：
  · 给**所有**人脸重新分组（不是只针对未命名的）
  · 但**手工命名过的脸会强制保住**（先拍快照，聚类后按名字归回）
  · **同名多组会保留**（作为可整理的中间状态，不自动合并）
```

所以可以放心反复调阈值试效果，名字不会丢。

### 单独处理"没分到脸"的人

```bat
venv\Scripts\python.exe app\reseed_people.py
```

对「标注了照片但一张脸都没分到」的人物，缩小范围（只在他自己标注的照片里）+ 放宽阈值重新播种。

## 七、知识库问答

### 怎么把文件夹变成知识库

```
文件夹 → 配置 → 勾选「作为知识库」→ 增量更新（或重建索引）
```

**注意**：知识库需要**正文**，所以模式要包含文字（不能选「相册」或「只索引文件名」）。

### 问答质量的关键

**检索质量 >> 模型能力。** 实测踩过的坑：

```
① 剪藏文章的正文里有大量 URL 编码垃圾（%2F %3F …）
   → 被当成"正文"喂给模型 → 模型只能说"资料里没有提到"
   → 用 clean_kb_chunks.py 清理

② 图片片段的 text 字段存的是**文件名**（哈希串）
   → 也被当成正文 → 同样污染
   → 用 clean_md_images.py 清空

③ markdown 图片语法 ![](../_resources/x.jpg) 出现在正文里
   → 模型把链接原样抄进回答，又长又没用
   → 同样用 clean_md_images.py 清掉

④ 检索只取前 5 个文件 → 真正讲这问题的文章排第 6 位够不着
   → 界面上把 top_k 提到 7-10
```

**注意**：清理脚本会**修改数据库**，但 **.md 源文件不受影响**。

### 做完整清理

```bat
:: 先演练，看会删多少
venv\Scripts\python.exe app\clean_kb_chunks.py
venv\Scripts\python.exe app\clean_md_images.py

:: 确认后执行（会自动备份数据库）
venv\Scripts\python.exe app\clean_kb_chunks.py --apply
venv\Scripts\python.exe app\clean_md_images.py --apply
```

### 图片描述能不能被搜到 —— 两个必须对齐的点

打标写进库的描述**默认和文字片段不是同一套向量**，会出现「明明打了标却搜不到」。

`
① prompt 必须一致
   文字片段：engine.encode(texts, prompt_name="Document", dim=cfg.index_dim)
   图片描述：也必须用 prompt_name="Document"     ← 漏了就白打标

② 维度必须一致
   两者都要用 cfg.index_dim（本项目默认 256）
   描述若用默认 768 维，就和文字片段不在一个空间里了
`

**症状**：打标完成，知识库却搜不到图里的文字，或搜出来的全是无关内容。

**修法**：改好上面两点后跑一次重新编码（只重算向量、不调视觉模型，几分钟）：

`at
venv\Scripts\python.exe app\reembed_captions.py
`

**还有一点**：知识库检索只应比对 	ext 和 caption。
若把几万条**图片向量**也拿去和文字查询比，会算出虚高相似度，
把真正含关键词的片段挤掉（实测搜「河北大学」搜不到就是这个原因）。

### 上传图片提问

```
① 模型选带 👁 视觉 的（本地 Qwen2.5-VL-3B）
② 点「📎 附图」选图（最多 4 张）
③ 输入问题 → 提问
```

## 八、图片打标（让插图可搜）

### 为什么需要

```
剪藏文章的插图文件名是哈希：506ce0c5..._MD5.jpg
     ↓
一个中文字都没有 → 文字搜索永远找不到
     ↓
用视觉模型给每张图生成一段中文描述存进库
     ↓
「图里写的那个命令」也能搜到了
```

### 生成效果（真实样例）

```
书法作品  → "黑底白字的草书书法，横向书写着「啓新報」三个字，笔画飞动洒脱。"
软件截图  → "电脑桌面截图，显示 Adobe Extension Manager CS6、Photoshop CS6、阿里旺旺…"
Docker    → "Docker-compose 命令执行中，多个容器正在拉取镜像并启动。"
古籍目录  → "古籍目录页面，列出了多种书籍的价格和内容，包括《四史全书》《通鉴九通全书》。"
```

### 怎么用

**设置 → 图片打标**：

```
时段 [  ] ~ [  ] 点      范围 [obsidian ▼]
☐ 用外部模型打标
[开始打标]  [停止]
进度 391/7244 · 失败 0 · 模型 Qwen2.5-VL-3B
```

**时段功能**：填 `1 ~ 7` = 只在凌晨 1 点到 7 点跑，其余时间**自动暂停**（不退出任务，到点自动继续）。

**这是一次性任务** —— 打完标以后搜索不再需要视觉模型。

### 显存问题（重要）

```
视觉模型 3B = 7.5 GB，占满 8 GB 显卡 → 桌面只剩 138 MB → 电脑卡顿

三个解法：
① 用时段控制，只在不用电脑时跑
② 设置 → 显存控制 → 「嵌入模型 → CPU」腾出 2.3 GB（搜索会慢 1-2 秒）
③ 用外部模型打标（不占本机显存）
```

## 十三、接到自建的 Dify 用（外部知识库）

**为什么不把数据导进 Dify**：Dify 只接受文档，不接受外部向量 —— 导进去它就会用
自己的嵌入模型重新切分、重新向量化一遍。你这套库里 300 多万字正文和 7000 多条
图片描述都得重算，而且会丢掉本项目的融合检索（向量 + 字面关键词注入 + 图片描述）。

**所以走 Dify 官方的「外部知识库」**：Dify 每次提问时来**调本服务**做检索，
知识始终留在本机，不用重建、不用重复嵌入。Dify 那边只负责编排和对话。

### 三步配好

```
① 本机：在 config.ini 的 [dify] 段填一个密钥（随便一串，别太短）
         api_key = 你的密钥
   然后重启服务（stop.bat → search.bat）

② Dify：设置 → 外部知识库 API → 添加
         API Endpoint : http://<本机在局域网的IP>:8199
         API Key      : 和上面填的一模一样

③ Dify：知识库 → 创建 → 选「连接外部知识库」
         External Knowledge ID : all
         （只查某一个知识库就填文件夹 id，例如 36；或路径关键词，例如 obsidian）
```

### 两个必须注意的网络点

```
· 本服务要监听 0.0.0.0（config.ini 的 [server] host），否则 Docker 里的 Dify 连不上
· Dify 在容器里访问宿主机：
    Linux  : 用宿主机的局域网 IP（如 http://192.168.1.10:8199），
             或者在 docker-compose 里给 Dify 加 extra_hosts: host.docker.internal:host-gateway
    桌面版 : 直接填 http://host.docker.internal:8199
· 只想内网用：防火墙限一下网段；**不要**直接暴露到公网（本服务除这个接口外没有鉴权）
```

### 自检（配之前先跑这条）

```bat
curl -H "Authorization: Bearer 你的密钥" http://127.0.0.1:8199/dify/info
```

它会告诉你：密钥对不对、有哪些知识库文件夹、各有多少片段、嵌入模型加载好没有。

### 行为说明

```
· 接口：POST /dify/retrieval（Dify 会在你填的地址后面自动补 /retrieval）
· 返回：{"records": [{"content", "score", "title", "metadata"}]}
        metadata 里带原文件路径、目录、file_id，方便在 Dify 里追溯来源
· 打分已归一化到 0~1：本项目的原始分数会超过 1（实测 1.185），
  而 Dify 约定 score 是 0~1 并拿它做阈值过滤 —— 所以这里按「本次最高分」归一，
  1.0 = 本次最相关的那条。Dify 里设的相似度阈值因此是「相对于最佳命中」的意思。
· 空查询返回 {"records": []}；没设密钥时返回 403 并说明怎么设（不会默默放行）
· Dify 对这个知识库**只有检索权限**，改不了你的内容（这是它的设计，正好符合需求）
```

### 如果以后想把重活放到服务器上

`/dify/retrieval` 只读索引库里的文字，**完全不碰原文件** —— 所以服务器上不需要同步
NAS 的几百 GB 原图，只要能读到 `data\index\index.db` + 模型权重就够了
（这两个文件夹的那些文件本身能否打开，只影响「预览原文件」，不影响 Dify 检索）。

## 十四、部署到局域网 Linux 服务器（本机建库 + 服务器常驻）

**为什么要这么拆**：服务器没显卡，而建库（4 万多个文件的向量、人脸）必须用显卡；
但"随时能用"又要求服务 7×24 开着。所以：**本机负责建库，服务器负责提供服务**，
两边用双向同步把数据对上。

### 实际部署（192.168.1.10，Ubuntu 24.04）

```
/home/lingxi/                项目本体（代码 + venv + 模型 + 索引库）
  ├─ venv/                         自带 Python 3.12 的虚拟环境（CPU 版 torch）
  ├─ models/embeddinggemma-2/      嵌入模型（1.45 GB，从本机拷过去的）
  └─ data/index/index.db           索引库（266 MB）
/home/lingxi/knowledge/             本机同步过来的知识库数据
  ├─ obsidian/                     ← D:\notes\obsidian（8496 个文件 / 794 MB）
  └─ 公众号小红书/                  ← D:\notes\wechat（8 个文件）
/mnt/nas_photo/               ← 192.168.1.88:/photo     （NFS，34060 个文件）
/mnt/nas_shared/                  ← 192.168.1.20:/Shared   （NFS，1259 个文件）
```

服务用 systemd 管理（**开机自启、崩了自动重启**）：

```bash
sudo systemctl status lingxi      # 看状态
sudo systemctl restart lingxi     # 重启（改完 config.ini 要重启；启动约 2.5 分钟，CPU 加载模型慢）
sudo journalctl -u lingxi -f      # 实时日志
```

部署脚本都在 `run\deploy\`：

```
deploy_36.py        分步部署（preflight / upload / bootstrap / service / verify / all）
lingxi-bootstrap.sh 服务器上装依赖（python3-venv → venv → CPU 版 torch → requirements）
mount_nas.sh        挂两台 NAS 的新共享 + 写进 fstab（开机自动挂）
remap_on_server.sh  把库里的 Windows 路径改成服务器上的真实路径（带抽样验证）
```

### ⚠ 服务器上必须调的一个参数：CPU 线程数

实测（48 核）：编码一次查询 **48 线程 1.713 秒 / 24 线程 0.276 / 16 线程 0.205 /
**12 线程 0.202** / 4 线程 0.410**。小模型在核多的机器上开满线程反而互相抢，
**慢 8.5 倍**。systemd 里已经设好：

```
Environment=OMP_NUM_THREADS=12
Environment=MKL_NUM_THREADS=12
Environment=OPENBLAS_NUM_THREADS=12
```

改完效果：完整搜索从 11.5 秒 → **0.7~0.85 秒**。想自己再测：
`./venv/bin/python run/deploy/bench_cpu.py`。

### 路径换到服务器上：remap_paths.py 支持 Linux 目标

库里的路径是本机的 Windows 路径（`\\NAS\photo\...`、`D:\notes\obsidian`），
服务器上是 `/mnt/...`、`/home/lingxi/knowledge/...`。搬库之后跑一次重映射即可
（**不用重扫、不用重算向量** —— 向量挂在文件 id 上，id 不变）：

```bash
./venv/bin/python app/remap_paths.py --old '\\NAS\photo' --new /mnt/nas_photo --apply
```

要点：
· `--new` 以 `/` 开头 → 自动按 POSIX 处理，**剩余路径的反斜杠会转成斜杠**
  （不转的话 Linux 上把 `\` 当文件名的一部分，永远读不到）
· 不加 `--apply` 是演练，会拿库里第一条记录换算成新路径**试着读一下**，
  读不到就提示"先别执行"
· 执行前自动备份整个库

### 双向同步（本机 ↔ 服务器）

两个脚本，都是**增量**的（只传有变化的），都写日志到 `run\deploy\*.log`：

| 脚本 | 同步什么 | 方向 |
|---|---|---|
| `run\deploy\sync_data.py` | 知识库**文件夹**（obsidian、公众号小红书） | **双向** |
| `run\deploy\sync_db.py` | 索引**数据库** | 默认本机→服务器；`--pull-db` 反向 |

`sync_data.py` 用**三路比对**（上次状态 / 本机现在 / 服务器现在）判断哪边新，
比只看修改时间可靠，不依赖两台机器时钟一致：

```
两边一样           → 跳过
只有本机变了        → 推上去
只有服务器变了      → 拉回来
两边都变了（冲突）  → 谁的修改时间新用谁，另一份另存为
                     <文件名>.sync冲突-<哪边>-<时间戳>，两边各留一份，不丢内容
```

删除默认**只报告不删**（加 `--prune` 才真的删）—— 误删比多留一份糟得多。

`sync_db.py` 的双向体现在：推库之前先读走服务器上的「人物命名」，推完再补回服务器
**并且写进本机库**（只补空位，绝不覆盖已有名字）；界面偏好也是换库前读、换完写回。
所以你在服务器上给人物起的名字，推库时不会被本机的旧库覆盖掉。

**换库不用重启服务**：服务器上有个 `POST /api/admin/reload-db`（只允许本机调用），
它会关掉旧连接 → 原子替换文件 → 重开一份库。267 MB 的库大约 4 秒传完、1 秒换好
（重启一次要 145 秒）。

## 十五、服务器上的本地对话模型（llama.cpp + GGUF，纯 CPU）

**为什么要有它**：服务器没显卡、也不装本机 1.5B（CPU 上太慢），问答本来只能靠外部 API；
本地 GGUF 模型的好处是**离线可用、不花额度、数据不出内网**。

### 装了什么

```
/home/lingxi/llama/llama-b11580/        llama.cpp 官方预编译二进制（build 11580）
/home/lingxi/llama/models/              三个候选 GGUF（共约 6.8 GB）
systemd: llama-chat.service            开机自启，监听 127.0.0.1:8080（只本机）
  llama-server -m <模型> -c 8192 -t 32 --jinja -ctk q8_0 -ctv q8_0 --cache-reuse 256
```

下载通道（这网络环境很重要）：**GitHub 直连不通**（release 资产在
objects.githubusercontent.com）、走本机代理 `192.168.1.77:10810` 只有 9.6KB/s；
**llama.cpp 走 `gh-proxy.com` 镜像 2.9MB/s**，**模型从 ModelScope 直连 8MB/s**。

### 实测（这台 48 核 CPU，一次知识库问答 1567 token 上下文 + 300 token 回答）

| 模型 | 体积 | 常驻内存 | 一次问答总耗时 | 回答质量 |
|---|---|---|---|---|
| **Qwen3-4B-Instruct-2507** Q4_K_M | 2382 MB | 2.99 GB | **55~68 秒** | ✅ 带 `[n]` 引用编号，最贴合知识库问答 |
| **Qwen2.5-3B-Instruct** Q4_K_M | 2007 MB | ~2.5 GB | **33 秒** | 结构清楚，但不标引用编号 |
| Qwen3-1.7B Q4_K_M | 1.1 GB | ~1.5 GB | 30 秒 | ❌ 默认"思考模式"吃光 token 预算，回答空白 |
| 云端 opencode deepseek-v4.1-flash | — | 0 | **17 秒** | 最好 |

### ⚠ 三个必须记住的参数

```
① 线程数 32 最优，**48 线程会让生成速度崩到 0.57 t/s**（实测：24→16.7、32→17.8、48→0.57）
   和嵌入模型同一个病理：小模型在核太多的机器上互相抢
② --jinja：用模型自带的对话模板，否则 Qwen 系列会答非所问
③ Qwen3 系列默认开"思考模式"，会先把 token 花在思考上（1.7B 就是这样变空白的）。
   用 2507（非思考版）或 /no_think 指令，别直接用 Qwen3 原版
```

### 给别的机器/服务器调用（局域网共享）

llama-server 默认只监听 `127.0.0.1`（本项目自己用）。要**让局域网里别的服务器直接调**：

```bash
# run\deploy\open_llama_lan.sh 做的就是这件事：改成 0.0.0.0 + 并发槽 1→2
sudo nano /etc/systemd/system/llama-chat.service   # --host 0.0.0.0 --port 8080
                                                   # -c 16384 -np 2   ← 两槽，每槽 8192
sudo systemctl daemon-reload && sudo systemctl restart llama-chat
```

别的机器这样接（**OpenAI 兼容，实测流式也支持**）：

```
Base URL : http://192.168.1.10:8080/v1
API Key  : 不需要（llama-server 默认不校验）
模型名   : 随便填都行（实测 qwen3-4b 也认）；规范值是 GGUF 的完整路径
接口     : GET /v1/models、POST /v1/chat/completions（stream: true 可用）
并发     : 2 个槽；第 3 个并发请求会排队。上下文每槽 8192 token，
           对方要发更长的提示词就把 -c 调大（内存相应增加）
速度     : 生成 16~17 t/s；短问答 1~3 秒；带 1500 token 上下文的知识库问答约 40~56 秒
```

⚠ **没有鉴权**：开出去以后同网段任何机器都能用这台服务器的 CPU。想加一道门：

```bash
# 在 ExecStart 里加 --api-key 你的密钥，然后对方请求带 Authorization: Bearer 你的密钥
# 想关回去就把 --host 0.0.0.0 改回 127.0.0.1
```

## 十六、多套外部 API 配置（v2.0）

**问题**：以前「设置 → 外部模型」只有一套配置。在「本地 llama.cpp」和「云端」之间来回切，
每次都得重填地址/密钥 —— 而密钥是最烦的那一项。

**现在**：可以存任意多套（最多 12），设置里**并列折叠显示**，点一下就切。

```
▸ 1）本地 llama.cpp（服务器）  qwen3-4b   http://192.168.1.10:8080/v1   ✓当前使用
▸ 2）云端 opencode            deepseek-v4.1-flash  https://opencode.ai/zen/go/v1
＋ 新增一套 API
```

- 展开卡片 → 「编辑这套 / 设为当前使用 / 删除」；下面那个编辑框编辑的就是你选中的那套
- **密钥跟着配置一起存**，切回来不用重填
- **「设为当前使用」** 决定打标和默认问答走哪套

**知识库问答那里直接选**（不用进设置）：那个下拉现在分两组 ——

```
本机模型                        ← 显存/内存里加载的 GGUF
──────────────
外部 API
  本地 llama.cpp（服务器）· qwen3-4b
  云端 opencode · deepseek-v4.1-flash
```

（原来的「用外部模型回答」勾选框已被这个下拉取代：选「外部 API」组里的任一项就是走外部。）

**两台机器共享这份列表**：`sync_db.py` 每次同步会把两边的配置列表取**并集**写回两边，
所以在 PC 上加几套，服务器界面里也能看到，反之亦然。
「当前使用哪套」**故意不共享** —— PC 常用云端、服务器用本地 llama，各留各的更合用。

### 这一版修掉的坑（都踩过）

```
① 数据库"热重载"曾会留下已关闭的旧连接：设置页那条路径还在用它，报
   sqlite3.ProgrammingError: Cannot operate on a closed database（表现：设置页 500）。
   **已修好**：`store` 在项目里被五处各持一份（搜索路由 / 设置路由 / Indexer /
   app.state / engine 的模态回调闭包），现在改成"各作用域登记换连接钩子"
   （`app/dbreload.py`），换库时全部一起换；接口响应里的 `rebinds` 能看出每一处结果。
   同步脚本还会拿「设置页」当金丝雀，任何一步不对就自动退回"重启服务"。
   实测：三个作用域全 ok、金丝雀正常、统计一致，**11 秒**完成（重启要 145 秒）。
② 数据库指纹里含 WAL，界面一写偏好就"判定库变了"→ 会每 15 分钟白重启一次服务。
   现在配置列表**值没变就不写库**，从源头掐掉。
③「外部 API」下拉是页面初始化时渲染的，那一刻服务端偏好还没回来 → 看不到可选项。
   现在偏好回灌完成后、以及每次读状态时都补渲染一次（幂等）。
④ 127.0.0.1 的含义随机器变：服务器上 127.0.0.1:8080 是本机 llama，
   在 PC 上就变成"PC 自己的 8080"（什么都没有）。跨机要用局域网 IP。
⑤ 页面里选"第 1 套"时曾写进了"当前使用的那套"：因为 0 是假值，
   `idx || activeIdx()` 会把 0 当成"没设置"。已改成显式判断。
```

## 附：知识库检索排错清单

知识库「搜不到」通常不是模型不行，而是**检索链路**的某一环断了。
下面每一条都是实际踩过的坑，按顺序查。

### 1. 片段类型过滤（最容易犯）

正文片段的 `kind` **不止 `text`**：

```
text     正文（markdown、txt）
pdf      PDF 提取的正文      ← 白名单漏掉它 = 家谱搜不到人名
xlsx     Excel 提取的正文    ← 同上
caption  图片描述（打标产物）
image    图片向量（必须排除！）
```

**必须用黑名单**（只排除 `image`），不能用白名单。
用白名单一旦新增格式（docx/pptx）就会漏。

```python
# 对：
hits = store.search(vector, ..., exclude_kinds=("image",))
# 错（会把 PDF/Excel 的正文一起排除）：
hits = store.search(vector, ..., kinds=("text", "caption"))
```

### 2. 图片描述（打标）的向量必须和正文对齐

```
① prompt 一致：都要 prompt_name="Document"
② 维度一致：都要 cfg.index_dim（本项目 256）
```

漏了任一条，打标就等于白做。改完跑一次：

```bat
venv\Scripts\python.exe app\reembed_captions.py
```

### 3. 专有名词要靠字面匹配，不能只靠向量

向量搜索对**人名、地名、编号、书名、命令**不敏感。
家谱 PDF 的正文是空格分隔的人名列表，向量相似度很低。

所以检索里必须有一路**片段正文的关键词搜索**（`LIKE '%词%'`）。

### 4. 候选条目一定要先按分数排序

```python
hits.sort(key=lambda h: -h["score"])   # 少了这行，后面全是白搭
for item in hits:
    if len(chunks) >= top_k:
        break                          # 满了就停，队尾的永远轮不到
```

**症状**：关键词兜底明明「补了 N 个文件」（日志里能看到），
结果里却一个都没有 —— 因为它们被追加在队尾，而循环提前 break 了。

### 5. 取片段时不能只翻前几片

```python
# 错：只翻前 10 片
SELECT text FROM chunks WHERE file_id=? ORDER BY seq LIMIT 10
# 而关键词可能在第 17 片（家谱 PDF 就是这样）
```

关键词命中的文件，要**先精确捞出含该词的那一片**，再补其它片。

### 快速自检命令

```bat
:: 某个词到底在不在索引里
venv\Scripts\python.exe -c "import sqlite3;c=sqlite3.connect('data/index/index.db');print(c.execute(\"SELECT COUNT(*) FROM chunks WHERE text LIKE '%关键词%'\").fetchone())"

:: 看各类片段的分布
venv\Scripts\python.exe -c "import sqlite3;c=sqlite3.connect('data/index/index.db');[print(r) for r in c.execute('SELECT kind,COUNT(*) FROM chunks GROUP BY kind')]"
```
